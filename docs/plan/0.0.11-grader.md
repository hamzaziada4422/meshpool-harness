# 0.0.11: the independent grader

Problem: an agent never grades itself. On a big task it can say "done" with a file missing, a number wrong or an instruction ignored. The grader is a second, separate check that runs before the agent reports back. It is on by default and works in Code and in Chat/Cowork.

The standard it grades against: would the user accept this as what they wanted?

## What triggers it

It runs when the agent is about to give its final answer and the turn was large. Any one of these counts:

- a plan (todo list) with 3 or more steps
- an approved plan (the turn right after a plan-mode turn)
- 12 or more tool steps
- files were made or changed, the request asked to build or make something, and there were at least 3 tool steps
- a long written answer (1,800 characters or more) after at least 4 tool steps
- a research answer: 4 or more search or fetch calls and a reply of 800 characters or more
- a long job on the deep lane with at least 6 tool steps

It does not run for simple questions, short tasks, plan mode, sub-agents, or when it is switched off. The user can always force it:

- the "Check this" button under a reply (works even when the switch is off)
- `/grade` in the terminal

A forced check grades the last piece of work once. It does not start a rework round. In the app the card then offers "Ask the agent to fix these".

## How it stays independent

The grader is a separate model loop (`agent/grader.py`, `GraderAgent`):

- fresh context and its own system prompt; it never sees the agent's messages or reasoning
- it is given only: the user's request(s), the plan with statuses, the agent's final answer, the files changed, and the commands run with exit codes and the last lines of output
- it first writes down what the user expects (explicit asks, and implied ones: audience, format, file type and name, length, tone, language, numbers that must be right, things not to do, what done looks like), then checks the real result against that list
- it treats the agent's claims as claims. Missing evidence counts as not met
- it is read-only: `read_file`, `grep`, `glob`, shell commands that only read, and the project's own test commands (pytest, npm test, go test, cargo test and similar, with no chaining or redirects). For office files and pages it also gets `read_document`, `check_deck`, `check_workbook`, `check_document`, `measure_office_file`, `view_output`, `ui_audit` and the web fetch and search tools when those exist. It cannot write, edit, make files, install, delegate or ask the user
- the project folder is listed (size and time) before it starts and compared after. Anything outside caches that changed is reported in the review's `touched` field. Nothing is reverted, because an editor or another process may change the folder while the grader works
- it uses `MH_GRADER_MODEL`, else the fast model (`MH_MODEL_FAST`), else the chat's model

It returns strict JSON: `verdict` (pass, partial, fail), `acceptance` (accept, accept_with_notes, would_send_back) with the one or two reasons that matter most to the user, `items` (requirement, status met / not_met / unverified, evidence), `blockers`, `fix`. The reader tolerates code fences, trailing commas and a cut-off tail, and asks once more if the reply cannot be read. A pass with an open item, or a "met" with no evidence, is turned into partial or unverified in code.

## The rework loop

If the verdict is partial or fail and at least one requirement is not met or there is a blocker, the findings (with the reviewer's fix instructions) go to the agent as a message starting `[Independent review]`. It fixes them and finishes, and the grader runs again. At most 2 rework rounds. Items that nobody could check (unverified) and suggestions alone are reported to the user but do not send the agent round again, so a clean job costs one review, not an extra loop.

If the grader fails (model error, timeout, bad JSON twice) nothing is blocked. The reply ends with "Independent check: it could not run (...). This work was not independently checked."

The final reply never claims more than the grader confirmed. It ends with a short section, for example `Independent check: all 6 requirements met.` or the list of what is not done and what could not be checked, with the reviewer's acceptance view.

## Limits

| Setting | Default | What it caps |
|---|---|---|
| `MH_GRADER_STEPS` | 15 | tool steps the grader may take. After that it gets one tool-less call to give its verdict |
| `MH_GRADER_SECONDS` | 240 | wall-clock time |
| `MH_GRADER_TOKENS` | 150000 | input plus output tokens (cached input counts) |
| `MH_GRADER_ROUNDS` | 2 | rework rounds |

Its tokens and time are counted in the chat's usage and shown in the receipt.

## What the user sees

- App: a small card under the reply, one line ("Independent check: all 6 requirements met", time and tokens), opening to the acceptance view, the reasons and the requirement list with Met / Not done / Could not check in words and evidence. Under a rework the card says the findings are going back to the agent
- Terminal: a compact block under the reply
- Headless `--output-format json`: a `review` object in the result; `stream-json` also carries the `review` events
- Receipts: the receipt line says `checked independently: 4 of 4 met (14 s, 33k tokens)`; the outcome log keeps a short `review` record. The Your work page ignores it

The `review` event: `verdict, acceptance, acceptance_reasons, met, total, items, expectations, blockers, fix, error, text, round, reason, rework, forced, secs, model, tokens{in,cached,out,calls}, touched`.

## Turn it off

- Settings, Features: "Independent check on big tasks"
- or `MH_GRADER=0` in the environment or `meshpool.config`
