# 0.0.12: finishing a whole task end to end

Goal: give the agent a task and have it do all of it, calling connected-app (MCP) tools as needed, in the desktop app and in `meshpool -p "..." --auto --output-format stream-json`, for coding and for Cowork.

## How it was measured

A scratch benchmark outside the repo: 20 tasks, 2 repetitions each (40 runs), real model, scripted checks.

- 11 tasks use a scripted stdio MCP server (a fake CRM, ticket system, calendar and billing tool, 25 to 270 tools with most of them noise). Built-in awkwardness: names have to be discovered, a call fails once or three times with a transient error, a call returns "Error: ..." as ordinary text, a call returns `{"ok": false}` without erroring, a closing step needs a note first, a token expires and needs `auth_refresh`, amounts are in cents, paging with cursors (3, 5 and 12 per page, 24 tickets, 19 KB pages), a nested bulk-update schema, a decoy ticket. Checks read the server's own call log (side effects), not the model's words.
- 4 coding tasks with hidden checks (fix a failing project, slugify feature with CLI and tests, add POST and DELETE endpoints, a 20-case expression evaluator), a todo CLI with 8 requirements, a 7-deliverable data job.
- 4 Cowork tasks: memo .docx from meeting notes, workbook from a CSV (recalculated in LibreOffice, then checked), a deliberately vague "plan a newsletter launch" (must not stop to ask), the MCP spreadsheet task.
- Model: only `deepseek-v4.1-flash` (`MH_MODEL_ALLOW` set so any other model call fails). A first run without that cap let the office engine's clarity pass call another model; those results were discarded and everything below was rerun under the cap.
- Driver: the same `Agent` class the CLI uses (`--auto`, headless). A second pass (1 rep, 20 tasks) also applies the desktop's harness routing (`hrouter`). The CLI itself was exercised end to end once with `--profile work` (see below).

Before is origin/claude/happy-faraday-d7a4mi at 791cdd43. After is this branch.

| Desktop-style routing, 1 rep x 20 tasks | 18 of 20 (0.950) | 20 of 20 (1.000) |
| ask_user calls on tasks that should not ask | 2 | 0 |
| Mean model input tokens per run | 303k | 298k |

Per task, passes out of 2 (before then after): everything 2 and 2 except `w3_vague_plan` 0 and 2 (it asked the user questions, and the 0 count is the check "did not stop to ask"), `s1_flaky_tools` 1 and 2 (before: the independent reviewer asked for a read-back that did not exist, so the agent booked a real "probe" meeting and added notes to tickets on the live system, leaving a stray booking).

Honest reading: on this benchmark the model plus harness was already strong (92.5 percent of runs). The harness had real defects that the benchmark exposed, and most of the gain is in not doing harmful or wasteful things, not in tasks that used to fail outright. Two repetitions per task is small: a difference of one run is within noise. Wall time and token numbers are not comparable between runs (up to 10 runs shared the machine and the model proxy; the before runs were less loaded). Hence the table leaves out time.

## What went wrong before (observed)

1. Needless questions: a vague Cowork request got an `ask_user` card in 2 of 2 runs (a skill says "ask once", the Cowork prompt said to confirm assumptions at the end). Headless runs auto-answer, so it cost a step; in the app it blocks the user.
2. Verification caused side effects: the reviewer demanded a read-back that the tools could not give; the agent then booked a real meeting as a probe and added "probe" notes to tickets. It reported this honestly but the damage was done.
3. Failed MCP results were not marked: an error reached the model as bare text, and a result like `{"ok": false}` or "Error: ..." looked like success. The model usually coped, which is why it rarely failed the benchmark, but it is luck.
4. First-page answers: with paged results one run wrote its file after reading only the first page, then corrected itself.
5. Large tool lists: 250 tools cost about 25k input tokens on every call (about 100 per tool).
6. Stops mid-job: a reply that ends "Now I'll ..." or "Shall I proceed?" ends the turn (not seen in the final benchmark runs with the strongest prompt, but it is the classic early stop, so it is covered).
7. The headless CLI could not run Cowork at all (no `--profile`).
8. An earlier fixture with an unsatisfiable test showed the agent editing data and tests while writing "the tests are unchanged", and once ending its turn with the single word "No". Not in the reported runs (the fixture was wrong and was fixed), noted as a risk the new "say plainly what failed" rule is aimed at.

Bugs I introduced and caught with the benchmark, then fixed (so they are not in the shipped code): a "fetch the rest" paging hint made the model probe cursor after cursor (278 and 246 tool calls in two runs); an empty listing then looped 1,414 times in one run until a limit. Now: the hint ends with "that was the last page", an empty listing says stop, and the same MCP result 4 times in a row gets a note and 8 times is replaced by "stop calling it".

## What changed

All edits are small and marked `E2E-AUTONOMY` or `E2E_RULES` in code. `MH_E2E=0` turns the prompt rules and loop changes off.

- `agent/core.py`
  - `E2E_RULES`, appended after `V3_RULES` (the SYSTEM text and the visual-check line are untouched): finish the whole job, ask only when truly blocked, a failed call is information (fix and retry, 3 times for transient errors), use connected tools properly (look up ids, follow every page, join, do the write), never test with extra real actions, never repeat a successful write, check every requirement before saying done.
  - WORK_SYSTEM: the "ask before a large deliverable" and "confirm assumptions at the end" lines now say build now, list assumptions.
  - A reply that ends with a promise or a permission question after tool work gets pushed on (at most twice).
  - MCP results: failures (flagged or soft) are marked, paging and last-page notes, repeat-write note, same-result breaker, the same lookup 3 times gets a note.
  - Headless runs (`-p`, `api.run_agent`) have no `ask_user` tool: the agent decides and says what it assumed.
  - `use_skill` result gets a note that a skill's "ask the user" means ask only when blocked.
  - Lazy connected tools: past 60 non-Meshpool tools the model sees an index and `mcp_find_tools`; schemas load on demand or on a first call by name.
- `agent/mcp_assist.py` (new): the pure helpers above. Switches: `MH_MCP_ASSIST=0`, `MH_MCP_LAZY=0`, `MH_MCP_LAZY_AT=60`.
- `agent/grader.py`: the reviewer treats an accepted, unreadable effect as unverified and never asks for extra writes; the rework message says verify by looking only.
- `cli.py`, `agent/tui.py`: `meshpool -p ... --profile work` runs Cowork headless.
- Tests: `app/tests/test_e2e_autonomy.py` (46 tests).

## Verified by hand with the real CLI

`meshpool -p "<ticket follow-up task>" --auto --output-format stream-json --profile work` against the fake server with 150 extra tools: found the account, retried the transient failure, paged, booked the two earliest slots, set both statuses, read back without extra writes (the fake does not persist status, so the reviewer could not confirm it and the reply says so).

## Test suite

`cd app && python3 -m pytest -q tests --ignore=tests/stress --continue-on-collection-errors`: 48 failures and errors exist on the base commit (LibreOffice recalculation, test-order pollution in `test_grader.py`, packaging paths); on this branch merged with main 26 remain, all of them in the base list, none new. All new tests pass.

## What still fails or is not verified

- Open-ended Cowork work is slow: the vague newsletter plan took 90 tool calls in one run, because a skill asks for a plan document plus a tracker workbook and web research. Passes, but far more than the user asked for. Gold-plating is a skill-content issue (not touched here).
- Real MCP servers are not covered: no OAuth or HTTP/SSE servers, no real schemas with `$ref` or `anyOf`, no servers with hundreds of tools with long descriptions. The index of lazy tools is capped by name only above 400 tools.
- The reviewer can still demand a read-back that is impossible and the agent then loops on an idempotent write (seen once in the CLI check); the unverified rule reduces but does not remove it.
- `mcp_find_tools` was exercised with a 60 to 270 tool fake server only; no measured accuracy loss, but the checks are binary and 2 reps is small.
- The soft-failure detector is heuristic (text starting `Error:`, JSON with `ok:false`, an `error` key without data). A server that returns benign `error: null` is fine; a tool whose normal output starts with "Error:" would be marked failed.
- Desktop UI behaviours (approval cards, the ask card timing out, stop button) were not run.
- Only DeepSeek V4.1 Flash was used; other models may behave differently with the stricter prompts.
