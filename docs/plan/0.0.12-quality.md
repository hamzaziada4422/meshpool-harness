# 0.0.12 code quality: report

Goal: what the agent builds (apps, dashboards, pages, games, CLIs, scripts, small backends) should be better in UX and in
functional correctness. Branch `claude/code-quality`, cut from the 0.0.11 line.

## What was measured

19 build tasks, phrased as a user would, each run once with the real model (DeepSeek V4.1 Flash) through
`python3 -m meshpool_harness -p "..." --auto --output-format stream-json`, in a scratch folder, once before and once after
the changes, in an identical setup (fresh `MESHPOOL_HOME`, same key, same browser tools, grader on).

Tasks: todo app, SaaS pricing page, dashboard for a CSV, snake, photo-rename CLI, notes REST API with tests, barber booking
form, pomodoro timer, duplicate-file script, expense tracker, kanban board, yoga studio landing page, markdown notes app,
URL shortener with a page and tests, CSV to JSON CLI for messy files, dashboard for a messy leads CSV (blanks, "$1,200",
"n/a", three date formats, duplicate row), habit tracker, static site generator with tests, invoice generator.

Scoring was objective and by use, not by reading code. Each web deliverable was driven with Playwright (headless Chromium,
`--no-sandbox`) at 1280 and 390 px: ui_audit, a click-through, and a task-specific script written by me (todo: add, empty
input, HTML injection, complete, edit, delete, reload; booking: empty, bad phone, bad email, blank name, past date, closed
Sunday, valid, reload; snake: start, steer, pause, game over, restart, touch; pomodoro: fake clock through a full session,
pause, reset, sound, tab title; kanban: add, drag, keyboard alternative, persistence). Code deliverables were run, their
tests executed, README and test files counted.

## Honest headline

The baseline was already good on the simple, well-specified tasks: the 0.0.11 grader and the build-ui starter produce pages
with no contrast, overflow or tap-target failures, and the todo, booking, dashboard and CLI outputs passed nearly every
probe. The remaining defects were few and concentrated in four places: dead anchors and buttons nobody clicked, template
fields left on a page, no tests or README for scripts and CLIs, and missing "expected but unstated" features (edit, pause,
best score, saved data). Counts below are small numbers from one run per task, so read them as direction, not as a
measured effect size. Model variance is real: an earlier baseline run (without the browser tools in its home folder, not
used in the table) showed a different set of defects.

## Systemic causes

1. Looking is checked, using is not. The prompts and skills required ui_audit (measurements). Nothing made the agent click
   every control, submit bad input, press game keys or reload. Dead links and dead buttons pass ui_audit.
2. The build skills said what to build in three lines. "A tracker" had no checklist of the features every tracker has, so
   the agent stopped at the first thing that worked (no pause, no edit, no best score, no persistence).
3. There was no skill at all for scripts, CLIs and APIs, so these got no tests-and-README discipline unless the model
   volunteered it. Two of six code tasks shipped without tests or README.
4. The grader had a generic rubric and no objective evidence for code. It could not see "this button does nothing".
5. A vague brief ("landing page for my studio") invited filler: bracketed template fields on the page, and the audit did
   not recognise them.

## Changes

- `ui_smoke.py` plus the `ui_smoke` browser tool (`agent/browser_mcp_server.py`, allowed in `harnesses/safe_tools.py` and in
  the grader's read-only list). It uses the page like a person: clicks every button and checks that something changed
  (page text, classes, table rows, downloads, popups), follows links, submits each form empty and with nonsense, tabs through
  the page, finds controls a keyboard cannot reach, presses keys in a game and checks the canvas or score changes, types an
  item and reloads to see whether it is kept, and collects console errors. It skips reset-like, export-like and already
  selected buttons so it does not cry wolf. Plain-words output in the same format as ui_audit.
- Grader (`agent/grader.py`): a new rubric step for anything built as code (features the user expects, no dead controls,
  states, validation, persistence, keyboard and phone, tests, run instructions), and automatic evidence put in front of the
  reviewer: the click-through of the HTML files the turn produced and measured code facts (test files, README). The
  reviewer is told a MUST FIX from the click-through is a real defect unless shown wrong. Switch off with
  `MH_GRADER_SMOKE=0`.
- Skills: `build-app`, `build-game`, `build-dashboard`, `build-website` rewritten with concrete feature checklists per kind,
  input and edge-case rules, and an explicit "use it, then reload" step ending in ui_smoke. New `build-code` skill for
  scripts, CLIs, APIs and backends (feature list, dry-run and exit codes, tests for edge cases, try it on messy input, a
  README of at most 40 lines). `build-ui` and `ui-review` gained the ui_smoke step and a "working" house rule.
- `ui_audit`: bracketed template fields ([Studio name], [city, postcode]) now count as left-over text.
- `agent/core.py`: one sentence appended to the existing visual-result rule, in both SYSTEM and V3_RULES, pointing at the
  matching build skill, the feature list, and use-it-like-a-user. Nothing in the loop logic was touched, to keep merging
  clean with the autonomy work.
- Tests: `tests/test_ui_smoke.py` (finds dead button, dead link, mouse-only control, console error, empty form accepted, lost
  data, inert game; passes a working page; grader evidence and rubric; skills and tool registration) and
  `tests/test_ui_template_fields.py`.

## Still weak

- Honest limits of the measurement: one run per task, probes written by me, the click-through also used as a scorer for
  the "before" side only. The before and after totals (12 and 2) are directional.
- The yoga page now leaves the timetable as "To be confirmed" on the page. That is honest, but it is still visible filler.
  The skill says to keep unknown facts off the page and list them in the reply; the model only half follows it.
- Pomodoro still has no desktop notification and kanban drag is mouse-only on touch. The skills mention a keyboard path for
  drag and drop but not touch drag; the click-through does not test touch drag.
- The agent leaves `ui-audit` and `views` screenshot folders inside the project's output folder. Not addressed here.
- ui_smoke is heuristic. It can miss a dead button whose effect is only a timer, and can flag a control that needs a prior
  state. It does not drive server-backed pages beyond what a browser click reaches. Multi-step flows (login, checkout) are
  untested.
- No check of how this feels in the desktop app on Windows or macOS; everything ran headless on Linux. The grader's new
  automatic evidence is covered by unit tests and was visible in the runs only as the reviewer citing the click-through; I did
  not inspect a grader transcript end to end.
- Existing installs get the new skill text only if the user never edited the old default (the 0.0.11 refresh rule).
