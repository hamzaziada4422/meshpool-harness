# 0.0.13: provider keys, Azure first

Goal: the Azure key works everywhere a model is called, and every common kind of key either works or is told apart with a clear message.

## What was built

- `core/endpoint.py`: one capability table (auth style, wire, token field, model list, defaults per provider) and pure functions: `detect`, `parse_pasted`, `build`, `adapt`, `explain`, `probe`. Used by `core/wire.py` (SimpleLedger), `agent/core.py` (the two URL/header lines in `_probe_once` and `_post`), `ui/settings_v2.py`, `ui/workbench.py`, `provider_setup.py`, `cli.ping`.
- Azure: classic (`/openai/deployments/{dep}/chat/completions?api-version=`, `api-key`), v1 (`/openai/v1`, no version), Foundry `/models` (version `2024-05-01-preview`), Claude on Foundry (`/anthropic/v1/messages`, `x-api-key`). Default api-version `2024-10-21`, user-overridable, accepted inside a pasted address.
- o-series and gpt-5 (also under custom deployment names): `max_completion_tokens`, no temperature, in the table.
- `core/key_relay.py`: local 127.0.0.1 relay so Pi, Hermes and OpenCode can use Azure classic and Foundry. Codex is configured for Azure classic with `query_params`.
- Environment detection: OpenAI pair, then Azure pair, used automatically; every other provider's key is offered with its own host only.
- Settings page: provider picker, deployment and api-version fields, working Test connection. Terminal: `/login` and `meshpool login` (onboard.py) ask for deployment and version. `agent/connect_cli.py` was left alone: it is for MCP connectors, not model keys.
- Redirects are never followed on these paths (OPENER), so a key header cannot move to another host.

## Verified with mock servers (app/tests/test_provider_keys.py, 148 tests)

The mocks refuse a request in the wrong style with that provider's own error (Azure wants `api-key`, bearer providers want Bearer and refuse `api-key`, Anthropic wants `x-api-key` plus version, o-series refuse `max_tokens` and temperature, classic Azure refuses unknown deployments and unsupported api-versions).

Also covered: pasted-address splitting, plain-words errors, env detection and order, keys never sent to another host (including a redirect on the chat path), saved Azure settings cleared when moving to another host, relay with a wrong token, harness config files for Azure.

## NOT verified

- No real Azure, OpenAI, Gemini, Bedrock or other key was available. Header and URL rules come from Microsoft Learn (v1 route, Claude on Foundry) and from memory of each provider's docs; real services may differ in details. Not confirmed against a real service: the Foundry `/models` route and its version, the Bedrock OpenAI-compatible hosts, Gemini behaviour with `stream_options`, GitHub `models.github.ai/inference`, Azure error code wording.
- Azure v1 is sent to agents as a Bearer key (Microsoft's OpenAI-client sample does the same) but this was not run.
- Codex, Pi, Hermes and OpenCode were not launched against Azure: their config files are tested, the agents are not installed here.
- Known gap: `agent/core.py` `_urlopen` (the agent loop) still follows redirects; fixing it was outside the two-line edit budget agreed with the other worker. The other paths do not.
- Real-model check: see the end of this file.

## Real model check

One streamed one-token call through `cli.ping` (SimpleLedger, new builder) to the default Meshpool endpoint with deepseek-v4.1-flash answered `ok` in 1.5 s: the default path did not regress. No other real model was called.
