## How to read it

- ID keeps the source ID. Platform audit rows are PA-<area>-<n>, numbered in the order of ALL_BUGS.md within each area (PA-extra rows are the "Extra" line at its top; PA-ND rows are the items its summary lists as not done). This branch's review rows are FL-<id>: H, M, L from the first pass, R and N from the rechecks, T found by tests, O the Office add-in review, S the second batch review, V the seventh review.
- Merged rows keep the first ID and list the others after "also". A platform audit item that is the same bug as a coordinator row is merged into that row, and its tests are added there.
- Severity: coordinator rows have none. Platform audit rows show its two tags as written, "kind / confidence" (for example "crash / high"). Review rows show high, medium or low.
- Status is one of: fixed; fixed (0.0.17), fixed by a gap-filling pass on this branch; already fixed; not reproducible; removed with the replaced design, followed by the test of main's equivalent behaviour; open, followed by why; won't fix. Words in brackets say what is partial or uncertain, and why.
- Test is a pytest node id or test file, relative to app/ (testkit paths start with ../testkit). A parametrized test is cited by its name without the brackets. Every id under app/tests was matched against pytest --collect-only on the current tree.
- Evidence: for coordinator rows, the fix files from docs/audit/ledger/<workstream>.md (no line numbers there). For the other rows, file:line in app/meshpool_harness (or the named folder) where the fix was found by reading the code; a bare file means the fix is there but the line was not pinned. "0.0.17 fix:" names where a gap-filling pass changed the code.
- Statuses of coordinator rows are copied from LEDGER.md and were not re-run. Statuses of platform audit and review rows were checked by reading the current code. The gap-filling passes ran their own new tests and checked that each fix test fails with the fix reverted; the full suite was not run for this ledger.
