Caveats stated once: (1) The scripted model calls `ls` once, then says "done", so tool results and model-driven branches (which office tool it picks, whether the grader triggers) are not exercised except where noted from the 13-call run and the baseline meter. (2) Prompt sizes of Codex and Pi come from their installed versions here (Codex 0.171 for the `codex` arm, Codex 0.166 inside codex-acp 2.6.0 for mp-on-codex). (3) "Extra calls" attribution from the meter uses prompt-size resets (a call whose prompt is under 70 percent of the previous call starts a new conversation); it is an inference, not a trace.

Notes on how the arms differ in what they send (read these before the tables):

* `pi` in bench3 is whatever `pi` is on PATH (0.73.1, system prompt 2.3k chars, 4 tools); `mp-on-pi` runs the Pi the app ships (1.5.2, vendored via `arms.pi_mp_src`). Vanilla 1.5.2 sends the same 1.4k, so the comparison is fair on size.
* `mp-cli` (`python -m meshpool_harness -p --auto`) gets no capability note and drops `ask_user`/`office_task` (headless; `_dropped` core.py:1020), so its request is 1.9k tokens smaller than mp-work's; both have the 226-char skills index. `mp-work` and `mp-on-*` go through `ui/agent_api.py` and get the capability note and the first-message block.
* With a non-OpenAI slug (`deepseek-v4.1-flash`), Codex sends plain function tools (`exec_command`, `multi_agent_v1`, goal tools; 13 tools, 18.1k chars) instead of the code-mode `exec` tool that its newer-model prompt uses. Meshpool's MCP tools then appear as 46 full schemas next to them.
* `mp-on-codex` also starts a second Codex session in the same codex-acp process to title the chat (requests 3 and 4 in the capture; 1 call in a real run).

## Headline

* **mp-on-pi, 23.5k per request, is 94 percent Meshpool.** Pi's own prompt and 4 tools are 1.4k. The skills catalog alone is 14.8k tokens (130 skills, descriptions in Pi's system prompt), the 46 Meshpool MCP tools are 5.6k, three extra Pi tools 0.55k, and boilerplate added to the user message 1.0k.
* **mp-work is only 1.3x Codex per request (13.0k vs 10.2k); the big gap is calls (68 vs 10).** Of the calls in the baseline meter, 322 of 381 mp-work calls and 291 of 360 mp-cli calls start a fresh conversation after the main agent (grader, nested engines, rework), against 0 for codex and pi. The per-request cuts are still worth 60 percent (tools are 65 percent of its request), but the call count is the bigger lever.
* **mp-on-codex pays 6.8k tokens over Codex per request: 5.5k for Meshpool MCP schemas (46 tools, 21.8k chars) and 1.0k for the user-message boilerplate, plus one extra 12k-token Codex session per chat** that codex-acp starts to write a title (on a hard-coded `gpt-5.6-luna` model, so it also shows up as a failed zero-usage call in the meter).

## Per-request growth (what is re-sent every turn)

Scripted 13-call run (request body KB per request, `captures13_sizes.txt`): mp-cli 44 to 51, mp-work 52 to 59, mp-on-pi 93 to 97, mp-on-codex 67 to 73, codex 40 to 46. With a result of `ls` the growth is only the assistant call and tool result (about 250 bytes) in every arm. Meshpool adds these items on top, all kept in the history and so re-sent on every later call:

* `[Meshpool]` user-role notes appended after tool results: `_v3_notes` agent/core.py:1819 [1871] (repeat-call and no-progress notes, in the 13-call run 12 notes of about 200 bytes), `_plan_note` core.py:1662 [1714] (a reminder every `EVERY=6` calls without a todo update, planning.py:11, plus "No plan yet" after 3 calls), the todo nudge (core.py:1414), the promise nudge (core.py:1427), grader findings (`INJECT`, grader.py:78).
* Tool-call arguments are not elided: `MH_ELIDE_OLD_CALLS` defaults to 0 (core.py:2021 [2073]), so every script or patch the model wrote rides along on all later requests (the comment at core.py:827 [829] documents 186k tokens in one 34-call task).
* Images: up to `MH_MAX_IMAGES=4` screenshots are re-sent on every call (core.py:2023 [2075]); `_attach_images` core.py:1871 [1923] keeps the latest two.
* Compaction only starts at `compact_chars` (core.py:1948 [2000], profile setting), so a 30-call run keeps growing; in the baseline, mp-on-pi grows 25.8k to 44.4k over 21 calls and mp-work 12.8k to 32.7k over 21, against codex 8.9k to 13.9k over 10.
* mp-on-pi / mp-on-codex: the first-message block (`ctx_pending`, ui/agent_api.py:873 [930]) is part of the first user message, so it stays in the harness's history for the whole chat. The capability note is appended on every message that names an office file (agent_api.py:837 [894]).
* Pi re-sends the whole 61k-char system prompt on every call; its `mcp.json` is read once per Pi launch (pi_rpc.py:137-142), so nothing there re-adds per turn.

### C. Per task, calls on the Meshpool loop (mp-work, mp-cli, and what mp-on-pi/codex reach through the MCP office server)

Order is by estimated calls saved on an office edit. Each item names where the calls come from.

1. **Independent grader.** `_grade_gate` (agent/core.py:1577 [1628], called at :1435 [1474]) fires when `large()` (agent/grader.py:182) says so: 3 or more todo items, an approved plan, 12 or more tool calls, files changed after a build verb with 3 or more calls, a long answer, 4 or more research calls. WORK_SYSTEM step 2 (core.py:255 [257]) and `V3_RULES` (core.py:177) tell the model to write a todo list for any multi-step request, so the first rule is met on nearly every office task. The grader is a full second agent (`make_agent` grader.py:558) with its own 4.1k-char system prompt (:49), 18 tools (9.8k chars; `MCP_LOOK` :41 lets office, browser and web tools through) and an evidence block of up to 14k chars: 4k to 8k tokens per call, up to `STEPS=15` calls (:29) plus a repair call (:77), `SECONDS=240`, `TOKENS=150000`, and up to `ROUNDS=2` (:28) rework rounds that re-enter the main loop (core.py:1596-1604).
